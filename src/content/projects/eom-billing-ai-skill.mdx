## The problem

At end of month, the PMO ritual is the same on every program: pull time entries from the PSA, cross-reference against SOW milestones, flag discrepancies, write a finance-ready summary. It's 3–4 hours of work per PM, per program, every month. Error-prone (manual copy-paste), inconsistent across people, and uses PM time that should go into the parts of the job that need actual judgment.

The data was structured and the process was repeatable. Strong candidate for automation.

## How I built it

**Watched my own week first.** Before writing a line of prompt, I worked through a couple of months of my own EOM by hand and listed what the agent would need to do: pull time data, compare against SOW budget, flag overages and underages, produce a plain-English summary for finance, surface anything weird for human review.

**Built on Glean rather than direct API.** Glean was already the PMO's knowledge and search layer. Building the agent there meant it could draw on live program data without me building separate integrations — less impressive on paper, much faster to ship and far easier for the rest of the PMO to adopt.

**Three chained prompts, schema-bounded outputs:**

- **Discrepancy detector** — compares billed hours vs SOW budget per program, flags severity.
- **Narrative generator** — produces the finance-ready summary in plain English.
- **Exception explainer** — for each flagged discrepancy, generates a probable cause and recommended action from program context.

**Guardrails.** Schema validation on every LLM output. If the model produced something that didn't parse, the skill surfaced the raw numbers for human review rather than silently producing a malformed summary.

## Outcomes

| Metric | Before | After |
|--------|--------|-------|
| Time per PM per program at EOM | 3–4 hrs | ~60–75 min |
| Discrepancy detection accuracy | n/a (manual) | >95% on the test set |
| PMO adoption | — | 100% within ~1 month |

## What I'd do differently

I built this and the Sprint Velocity agent against separate data pulls before I'd noticed they ingest almost the same program and sprint data. A shared data layer built once would have sped both up. That's the kind of detour you only notice once you've shipped the first agent — but next time I'd build the data layer second instead of in parallel.
