## The Problem

Coursera's analytics infrastructure had grown organically on Amazon Redshift for years. As data volumes scaled with the platform's global expansion, the team faced compounding challenges: slow query performance on large joins, rising compute costs, difficulty supporting concurrent data science workloads, and a lack of a unified data governance layer.

The business needed a modern lakehouse platform that could serve BI, data science, and streaming use cases — without disrupting the hundreds of dashboards and pipelines already in production.

## The Approach

The migration was structured in four phases to manage risk and keep production pipelines running throughout:

**Phase 1 — Discovery & Inventory**
Catalogued all 2,300+ Redshift objects (tables, views, stored procedures, UDFs) using automated schema extraction. Each object was classified by complexity, downstream dependency count, and migration risk level.

**Phase 2 — Architecture Design**
Designed the target Databricks Delta Lake architecture using a medallion pattern (Bronze → Silver → Gold), Unity Catalog for governance, and cluster policies for cost control. Migration tooling was selected and configured for automated SQL dialect translation.

**Phase 3 — Iterative Migration**
Objects were migrated in waves — starting with low-risk, low-dependency tables and working up to complex views and stored procedures. Each wave included data validation (row count checks, hash comparisons, and business rule assertions) before sign-off.

**Phase 4 — Cutover & Stabilization**
Ran dual-write for two weeks before final cutover, allowing downstream consumers to validate outputs. Post-cutover, a 30-day hypercare period monitored job SLAs and data freshness.

## Key Decisions

- **Chose Delta Lake over Iceberg** for tighter Databricks integration and mature ACID transaction support at the time of the project.
- **Kept orchestration in Airflow** (existing) rather than migrating to Databricks Workflows — reducing scope and risk for the initial cutover.
- **Ran validation in parallel** rather than sequentially — cutting validation time by 3x using distributed comparison jobs.
